WHY SAVE CORE LOADS BEFORE MAIN
===============================
The old main bootstrap attempts to find/load a campaign during startup. V11.8 installs the canonical persistence facade first, so startup can retain mature bootstrap behaviour without allowing legacy code to own Save/Storage.

OWNERSHIP MOVED TO CANONICAL CORE
=================================
core.storage
- Owns low-level persistence calls.
- Uses RF.Platform.active.storage.
- No gameplay system needs to know whether the backend is browser localStorage or a future Android/Capacitor implementation.

core.campaigns
- Owns campaign index and active slot.
- Owns checksum envelopes.
- Owns primary, backup, recovery and temporary verified writes.
- Owns slot create/rename/delete/duplicate/load/save-now.
- Preserves the V9.5 storage-key format exactly.

core.state
- Owns RF.newGame.
- Owns RF.save.
- Owns RF.load.
- Owns RF.exportSave.
- Owns RF.importSave.
- Owns new-campaign and import entry points.

core.migrations
- Owns historical-normalizer ordering.
- Owns all future explicit schema migrations.
- RF.V95.migrate now delegates to the canonical migration owner.

core.saveBoot
- Installs the historical migration registry after gameplay compatibility definitions exist.
- Re-normalizes and reconciles loaded state under the single canonical chain.

WHAT WAS PHYSICALLY REMOVED FROM ACTIVE LEGACY OWNERSHIP
========================================================
- RF.save/RF.load/RF.exportSave/RF.importSave definitions were removed from active js/legacy/base/state.js.
- The V9.5 campaign persistence implementation was removed from the active gameplay compatibility runtime.
- Historical wrappers that repeatedly replaced RF.newGame, RF.load and RF.importSave for migration purposes were removed from the active gameplay compatibility runtime.
- Historical RF.V95.migrate wrapper stacking was removed from active ownership.

The active gameplay compatibility runtime is now js/legacy/compat_gameplay_v1153.js.
The prior full js/legacy/compat_v1153.js is retained only for archive/audit comparison.

HISTORICAL NORMALIZERS
======================
78 historical migration/repair functions are registered by core.migrations in their established order.

Their function bodies remain temporarily beside the old gameplay patches where some depend on patch-local helpers/data. They no longer determine migration order or wrap public persistence APIs. Removing/reimplementing these bodies will happen naturally as the corresponding gameplay systems are migrated to canonical modules.

This distinction is deliberate: migration OWNERSHIP is fully canonical, while old normalization IMPLEMENTATIONS are compatibility dependencies until their systems are extracted.

ARCHAEOLOGICAL SHRINK
=====================
The active compatibility source no longer carries the V9.5 save manager or the repeated save/load/import migration wrapper stack. Approximately 28.8 KB of historical source responsibility was stripped while preserving the gameplay sequence.

The compatibility layer still contains mature gameplay and historical normalizer bodies. Subsequent extractions can now shrink that layer system by system without touching campaign persistence.

Moving those definitions behind RF.Catalog before expansion prevents the compatibility layer from becoming the content database for V12.
