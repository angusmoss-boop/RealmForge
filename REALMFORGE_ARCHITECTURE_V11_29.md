## V11.29 architectural changes

### Canonical content authoring
`js/data/authoring.js` registers canonical module `data.authoring` and exposes `RF.Authoring`.

The authoring surface is intentionally data-first. It provides:
- type-specific helpers for items, enemies, locations, recipes, quests, skills, NPCs and perks;
- generic `register` / `registerMany` methods;
- `registerPack` for coherent multi-type content packs;
- `defineConfig` for dotted canonical configuration keys;
- record validation;
- full Catalog cross-reference validation;
- Config/world cross-reference validation;
- `report()` and `assertClean()` for build/development gates.

`RF.Catalog.validate()` remains backward-compatible with the old string-error API. `RF.Catalog.validateDetailed()` exposes structured authoring issues.

The live V11.29 content graph validates cleanly. The authoring validator currently covers item drops, recipe inputs/outputs/skills, location links, NPC homes/schedules, perk prerequisites, quest links/objectives, global shop stock, event locations, markets, ecosystems, banks/inns, burglary loot, equipment stat configuration, exploration pools, dungeon definitions and V11.4 dungeon entity/gear registrations.

A copy-ready pack example lives at `content_templates/realmforge_content_pack.example.js`. The authoring rules are documented in `CONTENT_AUTHORING_GUIDE_V11_29.md`.

### Final compatibility classification
`js/core/compatibility_classification.js` registers canonical module `core.compatibilityClassification`.

Every remaining historical timeline entry in the active 64,639-byte compatibility runtime is explicitly classified:
- **80** `canonical_chronology_bridge`
- **12** `save_migration_bridge`
- **1** `mixed_historical_runtime`
- **0** `retireable_obsolete`

The sole mixed runtime stage is `js/v3.js`, where the captured `finishActivity` wrapper combines Dungeon Delve completion and Prospector Mining bonus logic. Splitting that wrapper without a multi-owner/scope-safe execution mechanism would change historical semantics.

V10.7 is no longer mixed runtime. Its actual code already lives in `core.scopedRuntime`; the compatibility entry is now only the chronology marker that invokes the scope-preserving capsule.

V11.29 therefore leaves compatibility at **64,639 bytes**. This is deliberate: no source is deleted merely to improve a legacy byte counter.

See `COMPATIBILITY_CLASSIFICATION_V11_29.txt` for all 93 boundaries.

## Authoring ownership rule
Future content should follow this decision tree:

1. **What exists?** Use `RF.Authoring`, `RF.Catalog`, and canonical content/config files.
2. **How does a mechanic behave?** Edit the canonical owner under `js/systems`, `js/ui`, `js/core`, or `js/platform`.
3. **Does it only preserve an old save or historical execution boundary?** Keep it in migration/compatibility infrastructure.

New content must never be implemented by adding a new chronological compatibility patch.

## Production bundle model
Readable canonical source remains the development source of truth.

V11.29 adds:
- `core.compatibilityClassification` to the Save / Platform / Lifecycle bundle;
- `data.authoring` to the Data bundle.

The Systems + UI payload is byte-identical to V11.28 because gameplay implementation did not change in this release.

All four production bundles are generated by concatenating their documented readable source order with one LF byte between source files. `CANONICAL_BUNDLE_PROVENANCE_V11_29.txt` records source hashes and final bundle hashes.

## Compatibility exit strategy
Compatibility is no longer a second gameplay architecture. Its remaining code is primarily historical ordering and save activation glue.

Future compatibility reduction requires proof of one of the following:
- a chronology bridge can be represented declaratively without changing ordering;
- migration activation can move to a canonical migration runner without changing old-save behaviour;
- the V3 multi-owner completion wrapper can be executed through a scope-safe composition mechanism;
- a stage is demonstrably obsolete under regression and save reconstruction.

Until then, keeping a small documented bridge is cleaner than manufacturing a false canonical owner.
